# Памятка для защиты лабораторной №3

1. Задача: отток клиента, Churn=Yes — положительный класс. 7043 клиента, 26.54% уходят.
2. Bagging усредняет независимые деревья, boosting последовательно уменьшает потери.
3. Разбиение 5634/1409, stratify, seed=42. Медиана и LabelEncoder обучены внутри каждого CV-фолда.
4. Четыре baseline, 200 деревьев/итераций, веса классов. Accuracy большинства 73.46% не решает задачу.
5. Главная метрика ROC-AUC; Precision/Recall/F1 зависят от порога, дополнительно PR-AUC.
6. Лучшая baseline по CV: Random Forest. Для тюнинга LightGBM заранее выбран методичкой.
7. Optuna: TPE, 30 trials × 5 фолдов, без holdout. Финальный выбор baseline/tuned LightGBM только по CV.
8. Итог: LightGBM (Optuna); CV ROC-AUC=0.8491, test ROC-AUC=0.8479.
9. SHAP объясняет raw log-odds, не процентные пункты вероятности. Сумма вкладов + base = raw score.
10. Summary — вся выборка, waterfall — один клиент высокого риска, dependence — tenure.
11. Полный pipeline принимает исходные поля; scaler не используется деревьями. Новая категория получает -1.
12. Локальный round-trip и GitHub raw проверены. Повторная HTTP-проверка: `python verify_remote.py`.

## Частые вопросы

- Почему не fillna до split? Это передало бы статистику test в train.
- Почему LabelEncoder? Требование задания; порядок искусственный, one-hot/нативные категории стоит сравнить.
- Почему CatBoost не лучший «из коробки»? Нативные категории в этом эксперименте не использовались.
- Почему score не точная вероятность? Веса классов меняют loss; нужна проверка калибровки.
- Зачем TenureYears, если есть tenure? Требование задания; дублирование может делить важность.
- Почему не обещаем выгоду от длинных контрактов? Связь не означает причинность; нужен A/B-тест.
- Что дальше? Калибровка, OOF stacking, SMOTENC внутри CV, порог по стоимости, временной holdout.
